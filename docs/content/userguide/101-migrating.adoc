=== Migrating Data to Newer Versions

When a major change is made to the GeoWave codebase that alters the serialization of data in a data store, a migration will need to be performed to make the data store compatible with the latest version of the programmatic API and the command-line tools.  Beginning in GeoWave 2.0, attempting to access a data store with an incompatible version of the CLI will propmpt the user with an error.  If the data store version is later than that of the CLI, it will ask that the CLI version be updated to a compatible version.  If the data store version is older, it will prompt the user to run the migration command to perform any updates needed to make the data store compatible with the CLI version. Performing this migration allows you to avoid a potentially costly re-ingest of your data.

For more information about the migration command, see the link:commands.html#util-migrate[`util migrate`] documentation.

==== Changes That Cannot Be Rolled Back

*RocksDB library, GeoWave 3.0.* GeoWave 3.0 uses RocksDB 10.10 (`rocksdbjni` 10.10.1.1), where
GeoWave 2.x used RocksDB 6.19.3. It opens a RocksDB store written by GeoWave 2.x in place, with no
migration or re-ingest. RocksDB's compatibility policy is that a newer release opens a database
written by any earlier release, as long as it is opened with unchanged options
(link:https://github.com/facebook/rocksdb/wiki/RocksDB-Compatibility-Between-Different-Releases[RocksDB Compatibility Between Different Releases, window="_blank"]),
and GeoWave 3.0 sets the same options as 2.x. It does not work the other way. From 9.0 on, RocksDB
writes new table files in block-based table `format_version` 6 by default, which RocksDB can only
read from version 8.6 on, so once GeoWave 3.0 has written a table file into a store, GeoWave 2.x
fails to open it with `Unknown Footer version. Maybe this file was created with newer version of
RocksDB?`. Opening a store can be enough to write one, because RocksDB flushes any rows left in the
write-ahead log to a new table file when it opens a database. If you might need to go back to
GeoWave 2.x, copy the store's directory before pointing GeoWave 3.0 at it.

==== Changes That Migration Cannot Handle

Some changes alter a store's encoding in a way that `util migrate` cannot read, so the data has to be
re-ingested.

*Filesystem store file names, GeoWave 3.0.* Every metadata entry and every data row in a
`filesystem` store is a single file whose name encodes that entry's key, and each partition of an
index is a directory named the same way. Earlier versions encoded those names with URL-safe base64,
whose alphabet uses upper and lower case to mean different things: `AA.bin` and `aA.bin` are the
keys `0x00` and `0x68`. On a case-insensitive filesystem -- which is the default for macOS APFS, and
the norm for Windows NTFS -- those are one file, so writing one of the two keys silently overwrote
the other's entry while keeping the other's name. The entry just written was then invisible under
its own key, and the entry it landed on was gone. 104 of the 256 one-byte keys collide this way, so
a store on such a filesystem was losing metadata and rows routinely rather than in a corner case.

Names are now encoded with unpadded base32hex, whose alphabet (`0-9A-V`) is single-case and, unlike
base64, orders encoded names the same way the raw keys order. `util migrate` cannot convert an
existing store: on the case-insensitive filesystems this fixes, entries were already lost, and there
is no way to tell which of the surviving files are the ones they claim to be. A 3.0 build rejects a
name it cannot read rather than guessing at it, so pointing one at an old store fails with an error
naming the file; re-ingest into a new store instead. If your store is on a case-sensitive filesystem
it was never affected by the corruption and its files are intact, so renaming each file and
partition directory from the old encoding to the new one is enough; note that base32hex names are
about 20% longer, which lowers the longest usable key from roughly 188 bytes to roughly 156 within a
255-character name limit.

*Redis data index, GeoWave 3.0.* Earlier versions encoded the data index with `fst`, which was the
default value of the `--serialization` option. `fst` cannot run on Java 9 or above at all -- it
reflects into private fields of `java.math.BigDecimal` while building its own configuration -- so
there is no version of GeoWave 3.0 that can read those entries in order to migrate them. The data
index is now written with Redisson's `ByteArrayCodec`, which stores the keys and values unchanged,
and the `--serialization` option has been removed; a store configuration that still sets it will be
rejected when it is loaded. This affects only the data index, which is written when secondary
indexing is enabled.

[[other-changes-3-0]]
==== Other Changes in GeoWave 3.0

*REST services no longer use Spring Security, GeoWave 3.0.* The REST web application
(`geowave-service-rest`) moved from Restlet to Jakarta REST (Jersey 3.1) and no longer uses Spring
or Spring Security. Its WAR needs a Jakarta Servlet 6 container, such as Tomcat 10.1 or later or
Jetty 12, rather than a `javax.servlet` one. The Spring Security configuration
(`security-servlet.xml`) and the Facebook OAuth2 example are gone; the example could not be loaded
by any Spring version GeoWave has shipped with. Configure authentication in the container instead,
with a `security-constraint` and `login-config` in `web.xml` (the file has a commented example), or
with a reverse proxy in front of it.

API keys still work, configured by the servlet's `api_key_db` init parameter, which names the
SQLite database file and replaces the `apiKeyDB` bean. The table is unchanged, so an existing
`ApiKeys.db` keeps its keys. When it is set, every request under `/v0` needs a valid `apiKey` query
parameter. A request with a missing or unknown key is now rejected with `401 Unauthorized`; before,
it got an empty response. The main page now shows each user only their own key; before, it showed
the key of whichever user had last loaded it.

The paths, parameters and JSON responses of the services are unchanged, so clients, including
`geowave-service-client`, need no change. A path that is not a service now returns `404 Not Found`
rather than the main page.

*GeoServer 3.0 and GeoTools 35, GeoWave 3.0.* GeoWave 3.0 is built against GeoTools 35.1 and
GeoServer 3.0.1, where GeoWave 2.x used GeoTools 25.0 and GeoServer 2.19. The GeoServer plugin
therefore needs GeoServer 3.0.x and cannot be installed in GeoServer 2.x. GeoServer 3.0 runs on a
Jakarta Servlet 6.1 container, such as Jetty 12.1 or Tomcat 11, and `geowave gs run` runs a
GeoServer 3.0.1 WAR.

* Java code built on GeoTools' `org.opengis` API has to move to `org.geotools.api`, the package
GeoTools 30 renamed it to. GeoTools ships an Ant script, `remove-opengis.xml`, that does the rename.
* Imaging moved from Sun JAI to Eclipse ImageN. Raster data and raster types written by GeoWave 2.x
still read.
* GeoServer 3.0 reads an unqualified geometry in a `CQL_FILTER` in the axis order of the request's
CRS. For a WFS 1.1.0 request with `srsName=EPSG:4326`, or with no `srsName`, that is
latitude/longitude, so a box such as `BBOX(geometry,-73,18,-72,19)` written as longitude/latitude
matches nothing. Name the CRS in the filter, for example
`BBOX(geometry,-73,18,-72,19,'CRS:84')`, to give coordinates as longitude/latitude.
* GeoWave code running inside GeoServer uses GeoServer's ANTLR, which is older than the one GWQL
needs, so GWQL queries are not available there. GeoServer itself does not use GWQL.

*S3 input uses the AWS SDK for Java 2, GeoWave 3.0.* Version 1 of the SDK reached end of support
at the end of 2025. GeoWave now lists and reads `s3://` input through s3fs-nio, on version 2 of the
SDK, instead of the `com.upplication` s3fs. The endpoint is still set with `geowave config aws`,
and paths keep their `s3://<endpoint host>/<bucket>/<key>` form.

* The filesystem's settings are system properties with dotted names: `s3fs_protocol` becomes
`s3fs.protocol`, `s3fs_access_key` becomes `s3fs.access.key`, and so on. `s3fs.region` and
`s3fs.path.style.access` are new.
* An `s3://` URL is now read from the configured endpoint, by the same client that listed it.
Before, it was always read from AWS, whatever the endpoint, so an S3-compatible store could be
listed but not read. The `s3.handler.protocol`, `s3.handler.userAgent` and
`s3.handler.signerOverride` properties are gone; `s3fs.protocol`, `s3fs.user.agent` and
`s3fs.signer.override` apply to reading too. The signer override is now the class name of an SDK 2
signer, and SDK 2 has no Signature Version 2 signer.
* Credentials come from the SDK's default chain, and GeoWave still falls back to anonymous access
for public buckets. The chain's system property for the secret key is `aws.secretAccessKey`, not
`aws.secretKey`.
* The signing region comes from `s3fs.region` or a regional endpoint such as
`s3.us-west-2.amazonaws.com`, then from `aws.region`, `AWS_REGION` or the AWS profile, and is
`us-east-1` otherwise.
